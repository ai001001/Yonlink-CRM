# 备份与恢复

适用：公网演示环境（`~/yonlink-deploy`，库 `yonlink_mvp_demo`）；其他环境同理，只需替换连接串与目录。

## 备份内容与方式
- **应用级逻辑备份**（服务器没有 pg_dump，见“设计说明”）：在一个 REPEATABLE READ 只读事务（一致性快照）内逐表导出为 gzip 压缩的 NDJSON。
- 表结构由迁移管理，不导出；清单记录已完成的迁移（名称与校验和），恢复时要求目标库迁移一致。
- **不备份会话**（sessions）：恢复后所有用户需重新登录。
- **附件**：只复制快照中被引用的文件（附件表与回收站快照中的附件），与数据库一致；磁盘上缺失的文件在清单 `attachments.missing` 中列出。
- 每个备份目录含 `manifest.json`，记录每个文件的 SHA-256；目录 700、文件 600；同一备份根目录同时只允许一个备份（`.lock`）；失败时删除不完整目录。

## 定时备份
- systemd 用户定时器 `yonlink-backup.timer`：每天北京时间 03:30（随机延迟 ≤ 5 分钟），错过则开机后补做。
- 服务 `yonlink-backup.service`：在 `current` 发布目录运行 `scripts/backup.ts`，读取 `shared/app.env`（数据库与附件目录）。
- 备份位置：`~/yonlink-deploy/backups/<UTC 时间>Z/`，保留最近 14 份（`BACKUP_KEEP`）。
- 模板：`deploy/systemd/yonlink-backup.service`、`deploy/systemd/yonlink-backup.timer`。

安装 / 更新：
```bash
cp deploy/systemd/yonlink-backup.service deploy/systemd/yonlink-backup.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now yonlink-backup.timer
```

常用命令：
```bash
systemctl --user list-timers yonlink-backup.timer      # 下次执行时间
systemctl --user start yonlink-backup.service          # 立即备份一次
journalctl --user -u yonlink-backup.service -n 20      # 最近一次结果
```

## 校验备份
```bash
B=~/yonlink-deploy; cd $B/current && set -a && . $B/shared/runtime.env && set +a
npx tsx scripts/restore.ts $B/backups/<目录> --verify-only
```

## 恢复演练（不影响线上，建议每月一次）
恢复到一个临时库与临时附件目录，核对后删除：
```bash
B=~/yonlink-deploy; cd $B/current && set -a && . $B/shared/runtime.env && . $B/shared/app.env && set +a
DRILL_URL=${DATABASE_URL%/*}/yonlink_restore_drill
# 1) 新建临时库并迁移到同一版本 / create and migrate a scratch database
node -e "const pg=require('pg');(async()=>{const c=new pg.Client({connectionString:process.env.DATABASE_URL});await c.connect();await c.query('DROP DATABASE IF EXISTS yonlink_restore_drill WITH (FORCE)');await c.query('CREATE DATABASE yonlink_restore_drill');await c.end()})()"
DATABASE_URL=$DRILL_URL npx prisma migrate deploy
# 2) 恢复 / restore
npx tsx scripts/restore.ts $B/backups/<目录> --target-url "$DRILL_URL" --attachments-dir /tmp/yonlink-restore-drill
# 3) 核对后删除临时库与目录 / check, then drop the scratch database and files
```

## 灾难恢复（覆盖线上，需负责人确认）
1. `systemctl --user stop yonlink-crm`（停止应用，避免恢复期间写入）。
2. 先对当前状态再做一次备份：`systemctl --user start yonlink-backup.service`。
3. 确认线上库迁移与备份一致（不一致时先用备份对应版本的发布目录执行 `prisma migrate deploy`）。
4. `npx tsx scripts/restore.ts <备份目录> --target-url "$DATABASE_URL" --attachments-dir "$ATTACHMENTS_DIR" --replace`
5. `systemctl --user start yonlink-crm`；所有用户需重新登录。

恢复脚本的保护：目标必须显式指定（不读取 DATABASE_URL）；先校验全部 SHA-256 与迁移，任何检查失败都不修改目标；
目标已有数据时必须加 `--replace`；写入在一个事务内完成（中途失败自动回滚）。

## 设计说明与限制
- 服务器上的嵌入式 PostgreSQL 只包含 initdb/pg_ctl/postgres，没有 pg_dump/pg_restore；安装客户端需要 sudo 或下载外部程序。
  因此采用应用级逻辑备份：数据精度不变（numeric、时间微秒、JSON、数组、枚举均按列名原样写回），但不包含数据库角色与库级设置（由部署脚本管理）。
- **备份与数据在同一台服务器上**：能防误删、错误迁移、数据被破坏，**不能防磁盘损坏或服务器丢失**。
  需要异地备份时，请提供存储位置（另一台服务器、对象存储等），再增加同步步骤；备份含客户数据，异地存储前应加密。
