# ADR-003 登录与租户识别

- 状态：**负责人已决策（方案 A + 调整）**；正式文本待 T0-A 最终决策清单统一批准后修订
- 日期：2026-11-08
- 关联：ADR-004、ADR-005、`docs/02-数据库ER设计.md` §3.1

## 0. 负责人正式决策（2026-11-08，决策 1/9）
负责人选择**方案 A**，并作如下调整，以下条款为本 ADR 的正式决策，优先于下文推荐内容：

1. 登录采用**租户 slug + 邮箱 + 密码**。
2. 单租户私有化部署支持配置**默认租户**；启用时登录页隐藏 slug 输入框，用户体验接近全局邮箱登录。
3. 多租户部署必须明确识别租户，**不允许根据邮箱自动猜测租户**。
4. 支持记住上次使用的租户，以及 `/login/{slug}` 专属登录入口。
5. 租户用户由所属租户管理员独立管理。
6. 平台运维账号采用**独立账号表和认证入口**，与租户用户认证域分离。
7. 登录前的用户查询只能通过受严格权限控制的 `SECURITY DEFINER` 数据库函数完成，固定 `search_path`，只返回必要的认证字段。
8. 业务数据只关联租户内部的 `users.id`，**不使用邮箱作为业务关联键**。
9. 为未来全局 `identities` 表和 `users.identity_id` 预留升级空间；**Foundation 0.1 不实现跨租户身份体系**。
10. 任何未来跨租户身份功能必须经过新的 ADR、安全评审和数据库迁移评审。

实施要点（随正式修订细化）：
- 默认租户为部署级配置（如 `AUTH_DEFAULT_TENANT_SLUG`），仅影响登录页展示与预填，服务端仍按 slug 解析租户并执行同样的校验；租户数 > 1 时该配置不得替代显式租户识别。
- “记住上次租户”仅为浏览器端便利（非 HttpOnly 偏好 Cookie 或本地存储），不作为任何安全依据。
- `users` 表 Foundation 0.1 **不建** `identity_id` 列；预留的含义是：不让业务表依赖邮箱、不把凭据字段散落到其他表，使未来以新增表 + 可空列的迁移完成升级。

## 1. 背景
- `users` 的唯一约束为租户内唯一（`UNIQUE(tenant_id, email)`），同一邮箱可在多个租户存在。
- 登录发生在租户上下文建立之前；启用 RLS（ADR-005）后，应用角色无法跨租户按邮箱查询用户。
- PRD 要求平台运维与租户业务管理员分离，平台运维默认不能读取业务数据。

## 2. 决策（推荐方案 A）

### 2.1 租户用户登录：租户标识 + 邮箱 + 密码
- 登录表单字段：`tenant`（租户 slug，全局唯一，小写字母数字和连字符）、`email`、`password`。
- 前端可记住上次使用的 slug（仅本地便利，不作为安全依据）；后续可按子域名自动填充（需公网方案批准后）。
- 登录前查询通过数据库函数 `auth.find_login_principal(slug, email_normalized)` 执行：
  - `SECURITY DEFINER`，属主为专用角色 `yonlink_auth`，`search_path` 固定；
  - 只返回 `tenant_id, user_id, password_hash, status, locked_until, failed_login_count`；
  - 应用角色仅被授予 `EXECUTE`，不能直接读取跨租户 `users`。
- 租户不存在、用户不存在、密码错误统一返回同一错误码与相近耗时（对不存在用户也执行一次哑哈希），防止枚举。
- 验证成功后，后续所有查询在 `SET LOCAL app.tenant_id` 的事务内执行。

### 2.2 平台运维登录：独立认证域
- 独立表 `platform_operators`（不含 `tenant_id`、不受租户 RLS 约束），独立登录入口 `/api/v1/platform/auth/*`。
- 平台运维会话与租户会话分属独立认证域（独立会话表、独立 Cookie 名，见 ADR-004 §2.8），互不通用；平台运维默认**无任何租户业务数据读权限**。

### 2.3 防暴力破解
- Valkey 计数：按 `IP`、`tenant+email` 两个维度滑动窗口限速。
- 数据库层：连续失败 N 次（默认 5）后 `locked_until` 短时锁定（默认 15 分钟），成功登录清零。
- 登录成功/失败写审计（不记录密码，邮箱按策略脱敏）。

## 3. 备选方案
| 方案 | 说明 | 结论 |
|---|---|---|
| B 全局唯一邮箱 | 整个安装内邮箱唯一，登录只需邮箱 | 简单，但集团多法人场景下同一人无法分属多个租户；跨租户泄露“邮箱已存在” |
| C 全局身份 + 租户成员关系 | `identities` 全局表 + `tenant_memberships` | 最灵活（一人多租户切换），但第一阶段复杂度与测试面显著增加；可作为后续演进 |

## 4. 影响
- ER 增加：`platform_operators`；`users` 增加 `failed_login_count`、`locked_until`、`password_changed_at`、`mfa_enabled`（预留）；唯一索引改为 `UNIQUE(tenant_id, lower(email)) WHERE deleted_at IS NULL`。
- 若负责人选 C，需在 T3 之前修订本 ADR 与 ER。

## 5. 验收
- 不存在租户 / 不存在用户 / 错误密码响应一致。
- 应用角色直接 `SELECT * FROM users` 在无租户上下文时返回 0 行。
- 平台运维会话访问租户 API 返回 401/403；租户会话访问平台 API 同样被拒。
- 限速与锁定测试通过。
