## 功能
- **相对日期（定时）**：线索创建日、商机创建日或预计成交日之前/之后 N 天（UTC 日期，0 表示当天）。
  - 触发日在规则创建日之后、且不早于 7 天前（停机补做上限）时执行；同一记录同一日期值只执行一次，日期改了按新日期再触发。
- **无跟进（定时）**：最近一次跟进（或记录创建时间）距今达到 N 天（1–365）；已转化线索、已结束商机不检查；每段沉默期只执行一次，有新跟进后重新计时。
- **执行**：条件在触发时按当前值判断，不满足则该触发键不再检查；动作与即时工作流相同（含 Webhook），以系统身份执行（通知与审计的操作人为空），记录执行次数与 `workflow.run` 审计。即时的新建/编辑不会触发定时规则。
- **定时任务**：`scripts/workflow-sweep.ts`，systemd 定时器 `yonlink-workflow.timer` 每 15 分钟运行（见 [定时任务](../deploy/定时任务.md)）。每条记录在独立事务内先登记执行键（`ON CONFLICT DO NOTHING`），并发运行时只有一个执行；每条规则每次最多 500 条，余下下次继续；损坏的规则被跳过，不影响其他规则；有规则出错时退出码为 1。
- **界面**：工作流规则的触发时机新增“相对日期（定时）”（日期字段、之前/之后、天数）与“无跟进（定时）”（天数）；列表显示“预计成交日前 3 天”“连续 7 天无跟进”等描述；编辑时回显。
- **演示数据**：新增 2 条——进行中的商机在预计成交日前 3 天提醒负责人；评分 ≥ 50 的线索 7 天无跟进提醒负责人。
- **不做**：按小时/分钟的定时、“动作延迟 N 天执行”（Zoho 的定时动作队列）、按工作日计算。

## 第一轮：功能测试
命令：`npx vitest run tests/scheduled-workflows/scheduled-workflows.r1-functional.test.ts`
结果：**4/4 通过（第二次运行通过，首次失败见下表）**。原始输出：[results/scheduled-workflows-r1-functional.txt](results/scheduled-workflows-r1-functional.txt)

覆盖：
- 校验：10 类非法设置 400（相对日期缺字段、字段不是日期、线索用预计成交日、缺天数、天数超过 365；无跟进缺天数、天数为 0、带字段、小数；新建时带天数）；合法设置保存并返回天数；即时新建商机与线索不触发定时规则。
- 预计成交日前 3 天：3 天后成交的执行、10 天后的未到、已赢单的条件不满足；通知发给负责人、操作人为空；再次运行不重复；赢单商机改回进行中也不再触发（该键已检查）；7 天后十天的那个到期；改预计成交日后按新日期再触发；执行次数 3。
- 创建日后 2 天：当天不触发、2 天后触发；触发日早于规则创建日不补；规则早已存在时 3 天前的触发日补做，20 天前的超过补做上限不补。
- 无跟进 7 天：10 天前创建的线索与商机各执行一次；已转化线索、已输单商机跳过；再次运行不重复；新跟进后 3 天不触发、8 天后再触发；列表返回天数。

### 失败与修复
| 现象 | 原因 | 修复 |
|---|---|---|
| R1 首次 1 项失败（[首次输出](results/scheduled-workflows-r1-first-run-failed.txt)） | 测试代码错误：该商机由管理员指派给销售，先有一条“指派”通知，查询时没有限定工作流通知类型 | 查询加上类型条件；4/4 通过 |
| R2 首次 1 项失败（[首次输出](results/scheduled-workflows-r2-first-run-failed.txt)）：把无跟进规则的天数改为空，数据库没有拒绝 | **真实缺陷（数据库约束）**：天数为空时 `BETWEEN` 的结果是“未知”，PostgreSQL 的 CHECK 把“未知”当作通过 | 新增迁移，约束中显式要求天数不为空；8/8 通过 |
| 相关测试 1 项失败（[输出](results/scheduled-workflows-r2-related-first-run-failed.txt)）：工作流演示规则校验 | 行为变化：规则新增 `triggerDays` 字段，已有用例校验演示规则时没有带上 | 用例补上该字段；28 个文件 334/334 通过 |
| E2E：工作流用例“共 6 行”变成 7 行 | 测试写法问题：新用例与已有用例共用测试库，新用例先新建了一条规则 | 已有用例改为只数演示规则（名称含“【演示】”）；10/10 通过 |
