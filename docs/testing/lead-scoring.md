# 线索评分 — 三轮测试记录

日期：2026-11-18　环境：同 [leads.md](leads.md)　参考：Zoho CRM Scoring Rules
迁移：`20261118150000_lead_scoring`
- 新表：
  - `lead_scoring_rules`：评分规则。
  - `lead_scoring_settings`：分级阈值，每个组织一行。
- 新枚举：`lead_scoring_rule_kind`。
- 新列：`leads.score`，带“组织 + 分数倒序”索引。
- 数据库函数与触发器：
  - `lead_score_items(lead)`：返回一条线索命中的规则及得分。只使用固定字段，不拼接 SQL。
  - 线索写入（BEFORE INSERT/UPDATE）时计算分数，客户端或直接写入数据库的分数都会被覆盖。
  - 跟进新增、删除，或修改关联线索、完成状态时，重算相关线索。
- 手工约束：
  - 分值在 -100 到 100 之间且不为 0。
  - 字段和取值按规则类型限定在固定集合内；跟进数上限为 1–50。
  - 阈值满足 0 ≤ 温和阈值 < 热门阈值 ≤ 1000。

## 功能
- **规则类型**：
  - 字段等于某值：来源、状态。
  - 字段已填写：公司、职位、邮箱、电话、手机、描述、来源市场活动、来源网页表单。
  - 已完成跟进：每条加分，最多计入若干条。
  - 规则可以停用；分值可以为负，例如“不合格”减分。
- **分级**：分数达到热门阈值为“热门”，达到温和阈值为“温和”，其余为“冷淡”。阈值由组织设置，默认 60 和 30。
- **自动计算**：由数据库计算，不依赖各个写入途径。手工新建、修改、导入、批量改状态、合并、转化、网页表单提交、回收站恢复、演示数据，以及跟进的完成、撤销、删除、改关联，都会自动更新分数。
- **保存规则**：整体替换规则和阈值，并在同一事务内重算本组织全部线索（使用咨询锁，同一组织的保存串行执行），返回重算的条数，写审计（记录规则文本的前后对比、阈值、重算条数）。
- **权限**：
  - 所有用户可以查看规则，也可以查看可见线索的得分明细。
  - 保存规则需要新权限 `scoring.manage`（管理员、经理）。
  - 线索接口不接受客户端提交的 `score`。
- **界面**：
  - 线索列表新增“评分”列，显示分数和分级颜色。
  - 新增“评分分级”筛选和“评分从高到低”排序；导出也按评分分级筛选。
  - “评分规则”按钮打开规则弹窗，没有权限的用户只能查看。
  - 线索详情显示分数、分级，以及命中的规则和分值。
- **演示数据**：11 条规则（来源、资料完整度、状态、网页表单、已完成跟进），热门阈值 50、温和阈值 25；演示线索三个分级都有。
- **不做**：按客户或商机评分、按时间衰减、按邮件打开等行为评分（第一阶段不做邮件集成）、评分变化历史。

## 第一轮：功能测试
命令：`npx vitest run tests/lead-scoring/lead-scoring.r1-functional.test.ts`
结果：**7/7 通过（第二次运行通过，首次失败见下表）**。原始输出：[results/lead-scoring-r1-functional.txt](results/lead-scoring-r1-functional.txt)

覆盖：
- **规则**：
  - 默认设置；保存后的顺序、阈值、重算条数。
  - 15 类非法输入返回 400：分值为 0、超出范围、小数；字段不在集合内；来源、状态取值非法；字段与类型不匹配；跟进数上限为 0 或 51；多余字段；超过 50 条；阈值相等或越界；客户端提交组织。
  - 审计记录规则文本前后对比、阈值、重算条数；只改阈值时审计只含阈值。
- **写入时计分**：
  - 空白公司不计分；停用的规则不计分；负分规则生效。
  - 客户端提交 `score` 时，新建和修改都返回 400。
  - 直接写数据库（更新和新建）时，分数会被触发器覆盖。
- **跟进**：
  - 未完成的跟进不计分；完成后计分；超过上限不再计分。
  - 撤销完成或删除跟进后扣回；把跟进改关联到另一条线索时，两条线索都重算。
- **重算与明细**：
  - 保存规则后已有线索按新规则重算。
  - 得分明细与分数一致，并给出分级和阈值。
  - 清空规则后分数归零；线索不存在返回 404。
- **列表**：
  - 按评分排序；按分级筛选；非法的分级、排序参数返回 400；修改阈值后分级随之变化。
  - 导出按分级筛选。
- **其他写入途径**：导入、批量改状态、删除后修改规则再从回收站恢复，分数都正确。
- **演示数据**：规则条数和阈值正确；每条线索的分数都等于其明细之和；三个分级都有线索；可以重复重置。

### 失败与修复
| 现象 | 原因 | 修复 |
|---|---|---|
| R1 首次 6 项失败：保存规则返回 500（[首次输出](results/lead-scoring-r1-functional-first-run-failed.txt)） | **缺陷**：规则校验用了 zod 的 `discriminatedUnion`，但“字段等于”按来源、状态有两种变体，类型值重复，zod 运行时报错（类型检查发现不了）；其余 5 项失败都是因为规则没有保存成功 | 改为普通 `union`（各变体仍为严格对象），并在注释中说明原因；重新运行 7/7 通过 |
| R2 首次 1 项失败：线索转化返回 400（[首次输出](results/lead-scoring-r2-integration-first-run-failed.txt)） | 测试代码错误：转化接口的参数应为 `account: { mode: 'new' }`，测试写成了不存在的 `createDeal` | 改正参数；重新运行 5/5 通过 |
| 新 E2E 首次 2 项失败 | 测试代码错误：①“客户推荐”来源的中文名写成了“转介绍”；②“分值 1”同时匹配“分值 10”“分值 11” | 改正文字；标签改为精确匹配；2/2 通过 |
