## 设计
采用“快照回收站”而非软删除：删除时在同一事务内把记录及随之删除的附属数据保存为快照，然后真正删除原记录。
因此所有列表、详情、统计、报表、搜索、导出、日历等查询都无需改动，已删除的数据不会出现在任何地方（软删除需要在每个查询加过滤，遗漏即泄露）。

- 快照内容：记录本身；备注、标签；只关联本记录的跟进（随记录删除）；与其他记录共享、只解除关联的跟进 ID；
  客户的联系人与转化来源线索；商机的产品明细、报价单（含明细）与转化来源线索。
- 恢复：一个事务内按原 ID 与时间写回；商机所属客户、产品明细中的产品必须仍存在，否则 409 并提示（条目保留）；
  已不存在的可选关联（标签、共享跟进、转化来源线索、线索的转化目标）跳过并在结果中说明。
- 组织 ID 一律取当前登录上下文，快照中的值不被信任。
- 报价单号：快照中的报价单号保留占用（`reserved_numbers`），新报价单不会复用，恢复时不冲突。
- 保留 30 天；访问回收站时清除过期条目，并以系统身份（操作人为空）写审计 `*.expire`。
- 权限：查看与恢复需删除权限（管理员、销售经理）；彻底删除与清空需新权限 `recycle.purge`（管理员）。
- 删除提示改为“记录将移入回收站，30 天内可恢复”；批量删除同样进入回收站。跟进、备注、产品、报价单的单独删除不变（直接删除）。
- 审计：`*.delete`（标记 recycled）、`*.restore`、`*.purge`、`*.expire`；审计日志页筛选新增对应动作。
- 接口：`GET/DELETE /api/recycle-bin`、`POST /api/recycle-bin/:id/restore`、`DELETE /api/recycle-bin/:id`。
- 演示数据重置时一并清空演示组织的回收站（旧快照对应已被重置的数据）。

### 失败与修复
| 现象 | 原因 | 修复 |
|---|---|---|
| 开发阶段生产构建失败（类型错误） | 测试代码：R2 中直接把对象写入 JSON 字段未做类型转换（Vitest 不做类型检查所以测试通过，Next 构建会检查） | 显式转换；重新执行 R2 并保存输出 |
| 开发阶段 E2E：两处定位失败 | 测试脚本：线索详情抽屉标题为“线索详情”而非线索名；“商机”“全部”匹配到左侧导航 | 改为按“线索详情”定位并检查内容；限定在回收站的类型切换控件内 |
| 既有用例 | 线索、客户删除成功提示改为“已移入回收站” | 更新线索与客户 E2E 中的提示断言 |
