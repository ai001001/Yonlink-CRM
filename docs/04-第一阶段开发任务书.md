# Claude Code — Yonlink-CRM 第一阶段开发任务书

> 本任务书用于项目初始化与 Foundation 0.1。当前阶段先设计和实现基础底座，不得抢跑开发完整 CRM 业务模块。

## 0. 执行原则

你是 Yonlink-CRM 项目的资深架构师和全栈工程师。先阅读仓库和 `docs/` 全部文档，再行动。

必须遵守：
1. 不擅自更换技术栈或架构决策。
2. 不一次性生成整个 CRM。
3. 不以静态页面或 Mock 数据冒充已完成业务。
4. 不允许前端作为权限控制的唯一位置。
5. 不信任客户端传入的 tenant_id、role、owner_id。
6. 不把密钥写入代码或 Git。
7. 所有数据库变更通过可审查 migration。
8. 每项任务必须有测试、文档和验收记录。
9. 遇到架构冲突先记录 ADR 并向项目负责人说明，不静默改变设计。
10. 不连接或修改任何生产服务器；只在本地开发环境工作。

## 1. 第一阶段目标

交付可本地启动的 Foundation 0.1：
- Monorepo 工程骨架
- Next.js 前端基础壳
- NestJS API
- PostgreSQL / Redis / MinIO 开发依赖
- 用户认证与安全会话
- 租户与组织基础模型
- 用户、部门、角色和权限
- 服务端租户上下文
- 审计日志
- 健康检查与结构化日志
- Docker Compose
- 自动化测试和 CI 基础

## 2. 第一阶段明确不做

- 不实现线索、客户、联系人、商机的完整 CRUD。
- 不实现工作流可视化设计器。
- 不实现自定义模块拖拽设计器。
- 不实现 AI 功能。
- 不实现营销邮件群发。
- 不实现复杂报表。
- 不为尚未进入阶段的模块创建大量空表。

### T3 — 数据库基础
仅建立：
- tenants
- organizations
- departments
- users
- roles
- permissions
- user_roles
- role_permissions
- auth_sessions
- audit_logs
- system_settings
- password_reset_tokens（决策 6-2，ER §3.11.2）
- email_outbox（决策 6-2，ER §3.11.3）

要求：
- UUID 主键。
- tenant_id 作用域。
- 时间戳和必要索引。
- 复合外键/唯一约束确保租户内关系。
- migration 可重复部署和可审查。
- seed 只创建本地开发演示租户和明确标记的开发管理员。
- 生产启动时不得使用默认弱密码或公开 seed。

- 授权版本（ADR-004 §2.3、ER §3.9）：`users.authz_version`、`tenants.authz_version`（`bigint NOT NULL DEFAULT 0`，`CHECK >= 0`）；`system_settings` 预置行 `authz.global_version`（0）与 `authz.cache_epoch`（UUID）；只增触发器；`user_roles`、`user_departments`、`role_permissions`、`roles`、`departments`、`permissions` 的版本递增触发器（语句级、`SECURITY DEFINER`、同一事务）。

- 部门状态（新增决定 A/C，ER §3.10.2）：`departments.status` **`NOT NULL`**（`active`/`inactive`/`deleted`）与 `deleted_at`，组合 CHECK `(status = 'deleted') = (deleted_at IS NOT NULL)`；有效部门 = `status = 'active' AND deleted_at IS NULL`；**`deleted` 为终态**，禁止恢复为 `active`/`inactive`，禁止修改已删除部门的 `deleted_at`；0.1 不提供部门恢复功能。
- 用户部门关系（决策 6-1，ER §3.10）：`user_departments` 复合主键 `(tenant_id, user_id, department_id)`、用户与部门复合外键（`NO ACTION`）、`FORCE ROW LEVEL SECURITY`；
  - D1 部分唯一索引（最多一个主部门）；
  - D2 `BEFORE INSERT/UPDATE/DELETE` 保护触发器（锁用户行 `FOR NO KEY UPDATE`；仅 INSERT 对部门行取 `FOR SHARE` 并校验有效；禁止改键列）；
  - D3 `DEFERRABLE INITIALLY DEFERRED` 约束触发器（提交前：无部门或恰好一个主部门）；
  - D4 部门状态触发器（新增决定 B：存在任何成员关联即拒绝停用/软删除，不区分用户状态；新增决定 C：拒绝 `deleted` 状态的任何恢复或 `deleted_at` 修改）；物理删除由外键 `NO ACTION` 拒绝；
  - D2/D3/D4 为 `SECURITY INVOKER` + `VOLATILE`，执行公共检查：`app.tenant_id` 与行租户一致、隔离级别必须为 `READ COMMITTED`（ER §3.10.5）；
  - 授权版本：成员关系变更递增 `users.authz_version`；部门 `parent_id`/`status`/`deleted_at` 变化递增 `tenants.authz_version`（ER §3.10.6）。
  - `yonlink_app` 列级最小授权（ER §3.10.10、ADR-005 §8）：`users` 仅 `display_name`、`locale`、`timezone` 直接可更新（重置路径的密码相关列经 `auth.consume_password_reset` 更新，其余受控业务列待 6-10）；`departments` 仅 `name`、`manager_user_id`、`parent_id`、`status`、`deleted_at`；`user_departments` 仅 `is_primary`；`tenants` 无 UPDATE；不得为加锁授予全表 UPDATE。
  - 部门上下级停用规则、部门树遍历语义属于 6-8，T3 不实现任何未批准规则（ER §3.10.12）。

验收：migration up/down 策略清楚；测试验证外键、唯一约束和租户关系；用户部门与部门状态测试 U1–U36（ADR-009 §3.5A，以真实 `yonlink_app` 权限执行）全部通过，U37 按 ADR-005 §7.2 评审结论执行；授权版本触发器测试覆盖用户级/租户级/全局变更、事务回滚不递增、版本不可递减（ADR-004 S11）。

### T4 — 认证
> 依据：ADR-003（登录与租户识别）、ADR-004（会话与 Web 安全，纯服务端会话）。浏览器会话**不使用 JWT 或 Refresh Token**。

- 登录（租户 slug + 邮箱 + 密码；单租户部署可配置默认租户并隐藏 slug；多租户不得按邮箱猜测租户）、登出、当前用户信息、活动会话列表与远程登出。
- 登录前用户查询与会话解析仅通过 `SECURITY DEFINER` 函数（固定 `search_path`，只返回必要字段）。
- 密码使用 Argon2id 哈希。
- 登录失败限速（Valkey）和短时锁定策略（数据库）。
- **会话创建**：256 位密码学安全随机 Session Token；数据库仅存 SHA-256 哈希；Cookie `__Host-yl_sid`，`HttpOnly; Secure; SameSite=Lax; Path=/`。
- **会话验证**：PostgreSQL 是会话有效性的唯一权威来源；**每个新请求**经 `auth.resolve_session()` 向 PostgreSQL 验证会话、过期、用户与租户状态；Valkey 不存储任何会话有效性数据；PostgreSQL 不可用返回 503（ADR-004 方案 Y）。
- **会话续期**：空闲超时（默认 120 分钟，15–480 可配）滑动续期，`last_used_at` ≤ 每 5 分钟写库且不影响空闲超时精度；绝对超时（默认 12 小时，1–72 可配）不可延长；“记住我”默认关闭，租户允许时 ≤ 7 天。
- **会话撤销**：登出、登录与权限提升后令牌轮换、并发上限（默认 5）淘汰最旧、修改密码、禁用用户、重大角色变更、租户停用；撤销事务提交后开始的新请求即被拒绝，不依赖任何缓存删除。
- **空闲超时精度**：`last_used_at` ≤ 每 5 分钟写库；API 进程内有界 LRU 记录最近活动时间，判定取较大值；进程重启后只可能提前 ≤ 5 分钟过期。
- CSRF：会话绑定（HMAC 派生）的双提交 Token + Origin/Referer 校验；不以 SameSite=Lax 作为唯一防护。
- 平台运维：独立账号表、独立会话表、独立 Cookie（`__Host-yl_psid`）和独立认证入口；默认空闲 30 分钟、绝对 8 小时、不支持“记住我”。
- **密码重置（决策 6-2 方案 A，ER §3.11、ADR-004 §2.4、ADR-005 §9）**：
  - 入口：普通用户自助（租户 slug/默认租户 + 邮箱，无需登录）；租户管理员为本租户用户发起（应用层校验本租户管理权限，不得跨租户，邮件发给目标用户，记录发起人、目标、租户、时间）；平台运维账号不走这两条流程（其他平台管理员或服务器命令行）。
  - 令牌：256 位密码学安全随机数，`password_reset_tokens` 只存 SHA-256；自助 30 分钟、管理员 24 小时（数据库 CHECK 保证）；一次性消费，单条条件 `UPDATE ... RETURNING` 防并发重复消费；不能作为登录会话，重置后不自动登录。
  - 申请接口一律 HTTP 202、响应一致、不存在的账号不发邮件；邮箱统一规范化；IP 只取 Nginx 设置的可信来源。
  - 限速：账号每小时 3 次、IP 每小时 10 次（Valkey）；Valkey 故障时账号限速由数据库计数兜底、IP 限速由进程内更严格限速器执行（ER §3.11.11）。
  - 链接：令牌只放 URL fragment；重置页 `Referrer-Policy: no-referrer`、`Cache-Control: no-store`、严格 CSP、无第三方资源；前端读取后立即清理 fragment；令牌、密码、明文载荷不得进入任何日志、追踪或 BullMQ 数据。
  - 确认事务：经 `auth.consume_password_reset` 在一个事务内原子消费令牌、校验用户/租户状态、更新密码哈希、撤销该用户全部 `auth_sessions`（`password_reset`）、撤销其他未使用令牌并取消其 Outbox 任务、写审计；任一步失败整体回滚。
  - 登录后主动修改密码：撤销其他会话，当前会话保留并轮换（`password_changed`）。
- **邮件投递（事务性 Outbox，ER §3.11.3–§3.11.8）**：
  - 令牌与 `email_outbox` 任务在同一 PostgreSQL 事务内写入；载荷以 AES-256-GCM 加密（密钥环在 `.env`，不入库，AAD 绑定行）；Worker 解密只在内存中进行。
  - Worker：`FOR UPDATE SKIP LOCKED` 领取、120 秒租约、围栏条件状态变更、发送前检查令牌状态、指数退避重试（最多 8 次且不超过令牌有效期）、永久错误直接失败、最终失败撤销令牌并告警；终态清理密文；每 30 秒轮询，BullMQ 只作唤醒。
  - 投递语义为至少一次：可能重复发送同一封邮件，但令牌仍只能消费一次。
  - 开发环境使用文件投递的本地邮件替身（`/home/ai/yonlink-data/dev/mail/`）；生产必须配置 SMTP。
  - 保留期：令牌与已发送/已取消任务 30 天，失败任务 90 天，由 Worker 分批清理。
- 预留 MFA，不把 MFA 假装成已完成。
- 记录登录成功/失败、登出、会话撤销审计事件；不记录密码、Session Token、CSRF Token 或 Cookie。

验收（对应 ADR-004 §5 安全测试 S1–S25 中的会话部分，全部必须通过）：
- 无效密码、不存在的租户/用户返回一致错误；限速与锁定生效。
- 会话创建：库中仅有哈希；登录前后令牌不同（会话固定测试通过）。
- 会话验证：篡改、过期（空闲/绝对）、已撤销令牌被拒绝；Valkey 停止、重启、恢复旧数据或被写入伪造数据时，认证仍由 PostgreSQL 正确判定（S8、S9）；PostgreSQL 不可用返回 503（S25）。
- 会话续期：空闲超时精确；绝对超时不可延长；“记住我”遵守租户策略。
- 会话撤销：撤销事务提交后开始的新请求被拒绝（S7，1,000 次循环零放行）；执行中的请求不保证中断（正式语义）。
- CSRF 与 Origin 测试通过；租户会话与平台会话互不通用。
- 日志扫描中不出现任何会话令牌、CSRF Token、Cookie 或密码。
- 密码重置与 Outbox：ADR-004 S6a–S6d 与 ADR-009 §3.5B（PR、PE、PL、PS、PO、PP 全部用例）通过；日志扫描中不出现重置令牌、明文载荷或完整收件人地址。

### T5 — 租户上下文与组织
- 用户必须归属 tenant。
- 认证成功后从数据库加载 tenant context。
- API 请求不得通过 body/query 覆盖当前 tenant。
- 后台任务必须显式绑定 tenant context。
- 组织、部门有层级关系和有效状态。
- 支持用户所属多个部门，但明确主部门（决策 6-1，ER §3.10）：
  - 用户可以没有部门；最多一个主部门；有部门时恰好一个主部门，只有一个部门时它必须是主部门。
  - 所有部门关系操作在单个 `READ COMMITTED` 事务内执行（流程 F1，ER §3.10.7）：先 `FOR NO KEY UPDATE` 锁定用户行，再读取当前关系并计算变更；主部门变更按“先取消旧主部门、再设置新主部门”的顺序；删除主部门且仍有其他部门时必须同时指定新主部门；删除唯一部门允许用户变为无部门；新增首个部门自动设为主部门。
  - 加锁顺序：用户行 → 目标部门行（`FOR SHARE`，由 D2 获取）→（语句末尾）版本行；全局顺序 `users`（`user_id` 升序）→ `departments` → `tenants`。
  - 批量操作（流程 F2）：在首条写语句前，按 `(tenant_id, user_id)` 升序**逐条语句**显式锁定全部涉及用户，不依赖多行 SQL 或触发器的处理顺序；任何涉及多个用户的事务（含 `user_roles` 与 `user_departments` 混合）同样适用。
  - 部门停用/软删除（流程 F3，新增决定 B）：先 `SELECT ... FOR NO KEY UPDATE` 锁部门行，再更新状态；只要存在任何成员关联（不区分用户是否启用）即由数据库拒绝；**不得**自动迁移成员或自动指定主部门；必须先由管理员逐一移除成员关联（遵守主部门规则）。
  - 同一事务内部门状态变更必须先于任何租户级授权变更（如 `role_permissions`）；管理操作默认一个 API 操作一个事务。
  - 对 `40P01`、`40001` 回滚并**重新执行完整事务**（重新加锁与读取，不只重试最后一条 SQL），最多 3 次；重试只是兜底，不能替代正确锁顺序，也不能彻底消除死锁。
  - 以上锁顺序与事务编排规则适用于 API、Worker 和所有后台任务；数据库强制的规则与调用方必须遵守的编排规则区分见 ER §3.10.7。
- 为 PostgreSQL RLS 预留事务级 `SET LOCAL app.tenant_id` 实现；策略与触发器经 `app.current_tenant_id()` 读取（空字符串视为缺失、格式错误报错）；禁止会话级设置；连接归还连接池前确认事务已结束（ADR-005 §7.3）。
- 租户选择只来自应用层已认证、已授权的会话上下文，`app.tenant_id` 不是租户身份认证；“一个事务只设置一次”的数据库级强制机制 ⏳ 待专项评审（ADR-005 §7.2），评审前不得宣称已具备该保证。

验收：Tenant A 用户无法通过篡改 URL、请求体或记录 ID 访问 Tenant B；连接池复用测试无上下文串租户；用户部门 API 的正向/负向与并发测试（ADR-009 U1–U36 的 API 层对应用例，含部门停用/软删除被拒绝、无自动迁移、已删除部门不可恢复）通过，前端校验不作为约束依据。

### T6 — RBAC 与数据授权基线
- 权限模型至少支持 resource + action + scope。
- 角色授予权限；用户通过角色获得权限。
- 初始角色：Tenant Owner、CRM Admin、Manager、Standard User、Auditor。
- 区分平台运维角色与租户业务角色。
- 服务端 Guard/Policy 对每个受保护 API 授权。
- 预留记录级共享、字段级权限接口；第一阶段不实现复杂可视化配置。
- 权限缓存（ADR-004 §2.3）：Valkey 只缓存权限集合，键包含 `cache_epoch`、全局版本、租户版本、用户版本；版本组合只取自本请求 `auth.resolve_session()` 的同一语句结果；未命中在 `REPEATABLE READ` 只读事务中计算，版本组合一致才回填；Valkey 异常回源 PostgreSQL；撤权生效不依赖缓存删除。

验收：不同角色访问受限 API 的正向/负向测试通过；仅隐藏前端按钮不算通过；ADR-004 S10–S13 通过（版本变化后旧缓存不可用、三级版本触发覆盖、并发权限变更零旧权限放行、恢复场景缓存纪元生效）。

### T7 — 审计
- 记录 actor、tenant、action、resource、before/after（敏感字段脱敏）、IP、user agent、request_id、timestamp。
- 审计记录 append-only。
- 普通用户无修改/删除权限。
- 审计查询按 tenant、时间、actor、动作过滤。
- 对密码、token、密钥、敏感字段做脱敏或排除。

验收：关键管理操作均生成日志；普通用户不能修改/删除日志；租户间不可查询。

### T8 — 前端基础壳
> 依据：ADR-001 §0A（Ant Design v6 + `@yonlink-crm/ui` 封装层）。

- 登录页（支持默认租户隐藏 slug、`/login/{slug}`、记住上次租户）、主布局、侧边栏、顶部栏、用户菜单、活动会话管理入口。
- 建立 `packages/ui`（`@yonlink-crm/ui`）：封装 Ant Design v6、`@ant-design/nextjs-registry`、`@ant-design/icons`、`ConfigProvider`（品牌主题 token + locale）；业务代码只能从此包引入 UI 组件。
- ESLint 规则：`apps/web` 禁止直接 import `antd`、`antd/*`、`@ant-design/*`。
- 不引入 Tailwind CSS 与 ProComponents；样式使用 Theme Token + CSS Modules。
- 中文默认、英文切换：业务文案 next-intl；组件内置文字使用 antd 语言包（`zh_CN`、`en_US`）+ dayjs locale。
- 用户语言、时区设置入口。
- 统一表格、按钮、表单、错误提示、空状态组件（紧凑型企业级密度）。
- 交付 `docs/design/visual-guidelines.md`：品牌主色与语义色、字体栈（不依赖外部字体 CDN）、圆角、间距、密度、表格/表单/菜单/仪表盘风格；不使用 Zoho 配色、图标或专有界面表达；经负责人审核。
- 仪表盘先只显示真实系统状态（含容量与备份时效）和基础统计，不制造虚假 CRM 业务数据。
- 适配桌面和移动浏览器。

验收：
- 登录状态正确；无权限菜单不显示且 API 仍独立校验（前端隐藏不构成安全控制）。
- i18n 不依赖硬编码中文/英文；切换语言后组件内置文字（分页、日期）同步切换。
- `pnpm lint` 能拦截业务代码直接 import antd 的违规示例（规则测试）。
- `next build` 在 ARM64 主机成功，记录构建峰值内存（应 ≤ ADR-007 预留的 2.5 GB）。
- 视觉规范文档经负责人审核通过。

### T9 — API 与文档
- REST API 版本前缀 `/api/v1`。
- OpenAPI/Swagger 文档。
- DTO 校验和统一错误格式。
- 分页、排序、过滤规范。
- request_id 贯穿日志。
- 速率限制与 CORS 白名单。
- API 变更记录兼容策略。

验收：API 文档可访问；所有输入经过服务端验证；错误不泄露堆栈和内部密钥。

### T10 — 测试与 CI
> 依据：ADR-009（Vitest 5 全仓统一 + RLS 集成测试方案）。

- 单元测试（Vitest，≤ 2 进程）：认证、会话、权限策略、租户上下文。
- 集成测试（Vitest，1–2 进程，每进程独立测试库）：数据库约束、RLS、审计、授权版本、权限缓存与故障注入。
  - 测试库由 `yonlink-crm-test` 模板库复制；**所有 RLS 集成测试以 `yonlink_app` 连接**，权限与正式运行时一致，不得通过提高权限让测试通过。
  - 首个测试为守卫测试：非超级用户、无 `BYPASSRLS`、非业务表属主、所有租户表强制 RLS、数据库名匹配 `yonlink_test_%`；失败则中止全部集成测试。
  - 密码重置与 Outbox 矩阵（ADR-009 §3.5B）：令牌、防枚举、限速与 Valkey 降级、会话撤销、Outbox 投递/重试/幂等/崩溃恢复、权限与租户隔离。
  - 用户部门与部门状态矩阵 U1–U37（ADR-009 §3.5A）：主部门规则、终态、成员前置条件、并发（U10 ≥ 500、U11 每种顺序 ≥ 200、U24 ≥ 200）、真实 `yonlink_app` 列级权限（U33）、连接池上下文清理（U34）、上下文缺失/格式错误/切换（U25、U35、U37）。
  - RLS 矩阵 R1–R11（ADR-009 §3.5）：跨租户读取/写入/插入/外键、无租户上下文、错误租户上下文、连接池上下文泄漏、并发隔离、新表覆盖、`SECURITY DEFINER` 函数、审计表只追加。
- E2E（Playwright，1 进程）：登录、登出、角色限制、跨租户访问拒绝。
- 单元、集成、E2E **串行执行**；运行集成/E2E 前停止 `next dev` 与 API/Worker 开发进程（ADR-007）。
- CI（`pnpm ci:local`）：install、lint、typecheck、unit、integration、e2e、build、migration check、依赖审计、密钥扫描。
- 覆盖率（`@vitest/coverage-v8`）：安全关键路径分支覆盖率 ≥ 90%；不因采用 Vitest 降低任何覆盖率、安全或 RLS 测试要求。
- 依赖漏洞扫描。

验收：CI 全绿；跨租户负向测试必须通过；守卫测试反向验证（故意以超级用户/属主连接时集成测试中止）通过；ADR-004 S1–S25 与 ADR-009 R1–R11 全部通过；失败测试不得被跳过来伪造通过。

## 5. 第一阶段里程碑

- M1：仓库骨架与 Docker 开发环境启动。
- M2：数据库模型与迁移完成。
- M3：认证和会话完成。
- M4：租户上下文与 RBAC 完成。
- M5：审计、前端基础壳、API 文档完成。
- M6：安全测试、CI、README 和演练完成。

每个里程碑需提供：
- 完成内容
- 变更文件清单
- migration 清单
- 测试命令及真实结果
- 未完成项与风险
- 下一里程碑计划

## 6. 第一阶段 Definition of Done

只有同时满足以下条件才能标记完成：
- 新环境依照文档可启动。
- 登录、退出和会话撤销正常。
- 用户、组织、部门、角色基础功能可用。
- 服务端授权生效。
- 跨租户访问负向测试通过。
- 审计日志可查询且不可篡改。
- 中英文框架可切换。
- 数据库迁移和开发数据 seed 可重复执行。
- 备份与恢复流程至少完成一次演练。
- CI 的 lint、typecheck、unit、integration、e2e、build 全部通过。
- 文档和进度文件更新。

## 7. 开始执行时的首条命令

请先不要写业务代码。执行以下工作：
1. 检查仓库现状和运行环境。
2. 阅读 `docs/` 中 PRD、ER 和架构文档。
3. 输出技术风险清单和待决策问题。
4. 提出第一阶段任务执行顺序和预计文件变更。
5. 生成/完善 `CLAUDE.md`、README、ADR-001 和 `docs/10-development-plan.md`。
6. 等待项目负责人确认后，再开始 T1。

## 8. 项目负责人验收方式

每个阶段由项目负责人根据验收表逐项验证。不得自行将“代码已生成”解释为“功能已完成”。发现测试失败、权限漏洞、数据隔离问题时，优先修复，不得进入下一阶段掩盖问题。
